# Повний підсумок завдання та реалізації

---

## Що будуємо

Сервіс генерації документів на основі шаблону та джерел. Користувач завантажує шаблон документа і одне або кілька джерел. Система аналізує шаблон, витягує релевантну інформацію з джерел, приймає рішення про наповнення кожної секції і таблиці, генерує новий документ зі збереженою структурою і форматуванням шаблону.

Це не просте підставлення даних — система використовує LLM для розуміння контексту, аналізу структури і прийняття рішень про те, що і куди помістити. Шаблон виступає як зразок структури і форматування, а не як форма з полями.

Обробка відбувається у фоновому режимі. Користувач може закрити браузер після відправки завдання, повернутися пізніше і завантажити готовий результат. Готові файли зберігаються на сервері.

---

## Де розгортається

Існуючий Flask додаток на Ubuntu сервері (openclaw), який працює під gunicorn і systemd. Новий сервіс додається як окремий Flask Blueprint до існуючого додатку — аналогічно до вже існуючого Blueprint для конвертації LaTeX в Docx.

---

## Технічний стек

### Веб-фреймворк
Flask — існуючий додаток. Новий Blueprint `doc_generator` інтегрується в нього без зміни основної структури.

### Фонова обробка
Celery — менеджер фонових задач. Отримує завдання від Flask і виконує пайплайн генерації незалежно від браузера і HTTP з'єднання. Запускається як окремий systemd сервіс.

Redis — брокер повідомлень між Flask і Celery. Зберігає чергу задач і їх статуси. Встановлюється як системний пакет Ubuntu і запускається як systemd сервіс.

### Парсинг файлів
python-docx — читання і запис docx файлів зі збереженням стилів, заголовків, таблиць і форматування. Використовується і для читання шаблону і для збірки фінального документа.

pymupdf (пакет fitz) — читання pdf файлів. Витягує текст зберігаючи структуру. Також перевіряє наявність текстового шару в pdf — якщо шару немає, файл є скановним і передається на OCR.

### OCR для сканів
pytesseract — Python обгортка для Tesseract OCR. Розпізнає текст зі сканованих зображень і pdf. Потребує встановлення системного пакету tesseract-ocr і мовного пакету tesseract-ocr-ukr для української мови.

Якщо якість Tesseract виявиться недостатньою на реальних документах — підключається Google Vision API (той самий Google акаунт що використовується для Drive). Це платний сервіс але з хорошою якістю розпізнавання українського тексту.

### LLM для аналізу і генерації
Gemini API (google-generativeai) — основний варіант. Моделі gemini-2.5-flash для більшості задач, gemini-2.5-pro для складних документів де потрібен глибший аналіз. Перевага Gemini — контекстне вікно до 1 мільйона токенів, що дозволяє передавати великі обсяги джерел напряму без RAG на першому етапі.

OpenAI API (openai) — резервний варіант. GPT-4o для reasoning, text-embedding-3-small для embedding. Підключається якщо Gemini не дає потрібної якості на конкретних задачах.

### Векторна база даних
ChromaDB — локальна векторна база даних без окремого сервера. Використовується для RAG коли джерела занадто великі щоб передати напряму в контекст LLM. Зберігає індекс між запусками — якщо ті самі джерела використовуються повторно, вони не переіндексуються.

### Валідація даних
pydantic — валідація JSON відповідей від LLM. Якщо модель повернула некоректну структуру — система робить повторний запит. Гарантує що кожен крок reasoning повертає очікуваний формат.

### Логування
loguru — логування кожного кроку пайплайну з часом виконання. Записує в файл. Допомагає діагностувати де система гальмує або помиляється.

### Утиліти
python-dotenv — завантаження API ключів і конфігурації з .env файлу.

## Як виглядає веб інтерфейс

Сторінка має дві частини. Верхня — форма завантаження файлів: поле для шаблону (один файл, docx або pdf), поле для джерел (кілька файлів, docx або pdf), кнопка відправки.

Нижня — список задач користувача. Зберігається в localStorage браузера — при поверненні на сторінку JS автоматично перевіряє поточний статус кожної задачі через API. Для кожної задачі відображається: дата створення, поточний статус (в черзі, в обробці з поточним кроком, готово, помилка), кнопка завантаження якщо готово, опис помилки якщо щось пішло не так.

Після закриття браузера і повернення — список задач відновлюється з localStorage і статуси оновлюються автоматично.

## Пайплайн обробки (що відбувається всередині Celery задачі)

### Крок 1 — Парсинг шаблону
`template_parser.py` читає шаблон і будує JSON опис його структури. Визначає всі розділи з заголовками і рівнями вкладеності, всі таблиці з кількістю стовпців і заголовками, стилі форматування (шрифти, відступи, стилі абзаців). Результат — JSON об'єкт який описує що є в шаблоні і яка логіка його наповнення.

### Крок 2 — Парсинг джерел
`source_parser.py` читає кожне джерело і перетворює на чистий текст. Для docx — python-docx. Для pdf — pymupdf перевіряє наявність текстового шару. Якщо текстового шару немає — `ocr.py` розпізнає текст через Tesseract з підтримкою української мови. Текст очищується від артефактів (колонтитули, розриви сторінок, зайві пробіли).

### Крок 3 — Стратегія роботи з джерелами
Якщо сумарний обсяг джерел відносно невеликий — текст передається напряму в контекст Gemini (до 1M токенів). Це простіший шлях без RAG.

Якщо джерела великі — `chunker.py` розбиває текст на чанки по 800 токенів з перекриттям 150 токенів. `embedder.py` перетворює чанки на вектори через gemini-text-embedding-004. `retriever.py` зберігає вектори в ChromaDB і надає інтерфейс для пошуку релевантних фрагментів під кожну секцію шаблону.

### Крок 4 — Reasoning і планування
`planner.py` робить виклик до Gemini API з промптом українською мовою. Промпт містить JSON опис структури шаблону і текст джерел (або retrieved chunks). LLM аналізує що і куди має йти, яка інформація відповідає кожній секції і таблиці, які рішення прийняти якщо даних не вистачає. Повертає JSON план документа. Pydantic валідує відповідь — при некоректному JSON робиться повторний запит.

### Крок 5 — Генерація контенту
`generator.py` проходить по плану і для кожної секції та таблиці робить окремий виклик до Gemini. Окремі виклики дають кращу якість і дозволяють оновлювати прогрес в task.json після кожного кроку. Для текстових секцій генерується текст в стилі ділового українського документа. Для таблиць генеруються дані рядок за рядком.

### Крок 6 — Збірка документа
`docx_builder.py` збирає фінальний документ. Копіює шаблон як основу, вставляє згенерований контент зберігаючи стилі абзаців і заголовків, будує таблиці копіюючи стиль рядка-зразку зі шаблону і додаючи потрібну кількість рядків. Зберігає результат в `data/tasks/{task_id}/output/result.docx`.

### Крок 7 — Завершення
Оновлює `task.json`: статус "готово", час завершення, шлях до файлу. Користувач при наступному відкритті сторінки бачить статус і кнопку завантаження.

## Systemd сервіси

Додаються два нових юніти поряд з існуючим gunicorn сервісом.

**Redis** — як правило після встановлення через apt вже має свій systemd юніт і запускається автоматично.

**Celery worker:**
```ini
[Unit]
Description=Celery Worker - Doc Generator
After=network.target redis.service

[Service]
User=your_user
WorkingDirectory=/path/to/flask_app
EnvironmentFile=/path/to/flask_app/.env
ExecStart=celery -A app.celery worker --loglevel=info
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

**Gunicorn** — збільшується timeout щоб не переривав довгі запити (хоча з асинхронною обробкою це не критично — Flask відповідає одразу з task_id):
```ini
ExecStart=gunicorn --timeout 120 --workers 3 app:app
```

## Етапи реалізації

### Етап 1 — Інфраструктура фонової обробки
Встановлення Redis. Підключення Celery до Flask додатку. Реєстрація Blueprint doc_generator в app.py. Тестова Celery задача (sleep 30 секунд) щоб переконатись що пайплайн Flask → Redis → Celery працює і задача продовжується після закриття браузера. Налаштування systemd юніту для Celery worker. Перевірка що всі три сервіси (gunicorn, redis, celery) стартують після перезавантаження сервера.

### Етап 2 — Веб інтерфейс і управління задачами
Форма завантаження файлів. Flask routes для відправки задачі і перевірки статусу. Збереження файлів в `data/tasks/{task_id}/`. Запис і читання `task.json`. Сторінка зі списком задач, автоматичне оновлення статусів через JS polling, кнопка завантаження готового файлу. На цьому етапі пайплайн ще не реалізований — Celery задача просто чекає і позначає себе як готову.

### Етап 3 — Парсинг файлів
`template_parser.py` — парсинг docx шаблону в JSON структуру з секціями, таблицями і стилями. `source_parser.py` — парсинг docx і pdf джерел в чистий текст. `ocr.py` — визначення сканованих pdf і розпізнавання через Tesseract. Тестування на реальних файлах щоб переконатись що структура витягується коректно.

### Етап 4 — Reasoning і генерація
`planner.py` — виклик Gemini API з шаблоном і джерелами, отримання плану документа у форматі JSON, валідація через Pydantic. `generator.py` — генерація контенту для кожної секції і таблиці з оновленням прогресу в task.json. Тестування на реальному шаблоні і реальних джерелах, оцінка якості результату.

### Етап 5 — Збірка docx
`docx_builder.py` — копіювання шаблону як основи, вставка згенерованого тексту зі збереженням стилів, побудова таблиць з нефіксованою кількістю рядків. Перевірка що форматування фінального файлу відповідає шаблону.

### Етап 6 — RAG (якщо потрібен)
Підключається якщо реальні джерела виявляться занадто великими для прямої передачі в контекст або якщо витрати на API стають суттєвими. `chunker.py`, `embedder.py`, `retriever.py` — побудова ChromaDB індексу і пошук релевантних фрагментів. Перемикання між прямим контекстом і RAG через параметр `USE_RAG` в конфігурації.

### Етап 7 — Шліфування
Обробка помилок на кожному кроці з записом в task.json. Очищення старих задач і тимчасових файлів. Логування через loguru з ротацією файлів. Перевірка роботи після перезавантаження сервера. На перспективу — банк джерел з можливістю вибору при створенні нової задачі.

## Ключові ризики

**Якість OCR** — Tesseract на складних сканах може давати помилки особливо з українським текстом. Вирішення: перевіряти на реальних документах на етапі 3, при необхідності підключити Google Vision API.

**Якість reasoning** — LLM може неправильно зрозуміти структуру шаблону або взяти не ту інформацію з джерел. Вирішення: детальні промпти українською мовою, покрокова генерація з валідацією через Pydantic, логування кожного виклику до API.

**Форматування таблиць** — python-docx має обмеження при роботі зі складними таблицями (злиття комірок, вкладені таблиці). Вирішення: детальний аналіз структури таблиць шаблону на етапі парсингу, копіювання стилів рядок за рядком.

**Витрати на API** — при великих джерелах і прямій передачі в контекст Gemini витрати можуть зростати. Вирішення: моніторити токени на етапі прототипу, при необхідності переходити на RAG або використовувати gemini-2.5-flash замість pro.
